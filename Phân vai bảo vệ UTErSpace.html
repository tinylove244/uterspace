UTErSpace được xây dựng theo kiến trúc MVC nhiều tầng (Multi-tier MVC) trên nền tảng Java EE 8 (Apache Tomcat 9). Để hiểu nhanh trong 1 phút, hãy nhớ đường đi của một request qua 6 bước tuần tự:

Bước 1 · Client

Trình duyệt (JSP + JS)

Giao diện render bằng JSP + JSTL. Các thao tác tương tác gửi fetch() / XMLHttpRequest kèm header X-CSRF-Token tự động gắn từ header.jsp.

Bước 2 · Filter Chain

4 Filter trong web.xml

Chạy đúng thứ tự: EncodingFilter (UTF-8 + Cache) → AuthFilter (kiểm tra session + đọc lại User từ DB) → AdminFilter (quyền ADMIN) → CsrfFilter (kiểm tra token POST).

Bước 3 · Controller

22 Servlet (@WebServlet)

Nhận request, kiểm tra dữ liệu đầu vào, kiểm tra quyền sở hữu / quyền xem (chống IDOR), điều phối gọi tầng Service hoặc DAO.

Bước 4 · Service

4 Lớp Nghiệp vụ dùng chung

ChatService, RelationService, NotificationService, RecommendationService — xử lý quy tắc nghiệp vụ phức tạp, gom thông báo, chấm điểm Bảng tin và đẩy sự kiện WebSocket.

Bước 5 · DAO & JPA

16 Lớp DAO + Hibernate

Tách Interface và Impl. Dùng JPQL hoặc SQL gốc (với tham số chống SQL Injection), quản lý transaction (begin / commit / rollback) qua JPAUtil.

Bước 6 · DB, Cloud & WS

MySQL 8.4 + Cloudinary + WS

Pool HikariCP kết nối MySQL 8.4 (24 bảng). File media đẩy lên Cloudinary CDN. Tin nhắn/thông báo đẩy tức thời qua WebSocket /ws (RealtimeHub).

1. Mật khẩu người dùng lưu trong DB như thế nào? Vì sao nhóm dùng BCrypt cost 12 mà không dùng MD5 hay SHA-256?

Giải thích sâu: MD5 và SHA-256 là hàm băm tốc độ cao (GPU có thể thử hàng tỷ chuỗi mỗi giây) và cùng một mật khẩu luôn ra cùng một mã băm nên dễ bị dò bằng bảng cầu vồng (Rainbow Table). Ngược lại, BCrypt tự động sinh 16 byte salt ngẫu nhiên trộn vào trong chuỗi kết quả (nên 2 người đặt cùng mật khẩu vẫn ra 2 chuỗi hash khác hẳn nhau) và với BCRYPT_COST = 12 (2^12 = 4096 vòng lặp), mỗi lần kiểm tra tốn khoảng 0,3–0,5 giây CPU, làm tê liệt các cuộc tấn công vét cạn (Brute-force).

Chỉ code: util/PasswordUtil.java — hằng BCRYPT_COST = 12 (L16), hashPassword (L23–25), verifyPassword (L34–38).

Giải thích sâu: Ngoài ra, trong realtime.js (L90–94), khi mất kết nối (trừ mã 1008 do bị khóa), trình duyệt tự động kết nối lại theo thuật toán Exponential Backoff (tăng dần từ 1 giây lên tối đa 30 giây cộng thêm độ lệch ngẫu nhiên 0–400ms để tránh hàng loạt máy cùng kết nối lại một lúc gây nghẽn server). public String join(int groupId, int userId, boolean privateGroup) {
    String status = privateGroup ? GroupMember.STATUS_PENDING : GroupMember.STATUS_ACTIVE;
    EntityManager em = JPAUtil.getEntityManager();
    try {
        em.getTransaction().begin();
        Group g = em.find(Group.class, groupId);
        User  u = em.find(User.class, userId);
        if (g == null || u == null) { em.getTransaction().rollback(); return null; }
        GroupMember m = new GroupMember(g, u, GroupMember.ROLE_MEMBER, status);
        em.persist(m);
        em.flush();   // Bắt lỗi trùng khóa chính kép (group_id, user_id) ngay trong khối try
        em.getTransaction().commit();
    } catch (PersistenceException dup) {
        if (em.getTransaction().isActive()) em.getTransaction().rollback();
        return null;
    } finally {
        em.close();
    }
    if (GroupMember.STATUS_ACTIVE.equals(status)) syncMemberCount(groupId);
    return status;
}

            .getResultList();

// DidKey.java — Tạo chuỗi did:key và Kiểm tra chữ ký Ed25519 (Dòng 31–62)
public static String fromPublicKey(byte[] raw) {
    if (raw == null || raw.length != 32) throw new IllegalArgumentException("Ed25519 public key must be 32 bytes");
    byte[] prefixed = new byte[34];
    prefixed[0] = (byte) 0xED;   // Multicodec prefix cho Ed25519 public key (0xED 0x01)
    prefixed[1] = (byte) 0x01;
    System.arraycopy(raw, 0, prefixed, 2, 32);
    return "did:key:z" + base58(prefixed);   // 'z' = Multibase Base58btc
}

public static boolean verify(String did, String message, byte[] signature) {
    if (message == null || signature == null || signature.length != 64) return false;
    byte[] raw = publicKeyOf(did);   // Giải mã Base58btc lấy lại 32 byte khóa công khai
    if (raw == null) return false;
    byte[] spki = new byte[ED25519_SPKI_PREFIX.length + 32]; // Ghép ASN.1 DER header (12 byte)
    System.arraycopy(ED25519_SPKI_PREFIX, 0, spki, 0, ED25519_SPKI_PREFIX.length);
    System.arraycopy(raw, 0, spki, ED25519_SPKI_PREFIX.length, 32);
    PublicKey pk = KeyFactory.getInstance("Ed25519").generatePublic(new X509EncodedKeySpec(spki));
    Signature sig = Signature.getInstance("Ed25519");
    sig.initVerify(pk);
    sig.update(message.getBytes(StandardCharsets.UTF_8));
    return sig.verify(signature);
}

  2. Xác thực chữ ký sinh trắc học 5 bước (WebAuthnService.verifyAssertion, L84–115): Khi quét vân tay qua navigator.credentials.get(), server kiểm tra 5 điều kiện bắt buộc của chuẩn WebAuthn:
    • (1) clientDataJSON có type == "webauthn.get", đúng challenge trong session (dùng 1 lần) và đúng origin.
    • (2) Mảng byte authenticatorData dài >= 37 byte, trong đó 32 byte đầu (rpIdHash) phải khớp chính xác với SHA-256(rpId) của tên miền máy chủ.
    • (3) Byte thứ 32 (flags): Cả bit 0 (UP = 0x01 — User Present) và bit 2 (UV = 0x04 — User Verified bằng sinh trắc học/PIN) đều phải bằng 1.
    • (4) Bytes 33..36 (signCount 32-bit big-endian): Nếu counter != 0 thì bắt buộc counter > key.getSignCount() đã lưu trong DB (chống sao chép bộ xác thực).
    • (5) Ghép mảng byte signed = authenticatorData || SHA-256(clientDataJSON) và kiểm tra chữ ký mật mã bằng SHA256withECDSA hoặc SHA256withRSA.
  3. Cửa sổ xác thực lại StepUp 5 phút (StepUp.java:14–40 & security.js:148–153):
